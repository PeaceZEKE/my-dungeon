# 캐릭터 모델링 뷰어

게임에 넣기 전에 캐릭터 하나만 따로 띄워 보고 다듬는 작업장. 새 캐릭터는 여기 있는 뷰어를
복사해 몸통 만드는 부분만 갈아 끼우는 식으로 만든다.

| 파일 | 내용 |
|---|---|
| `three.r128.min.js` | 게임 `index.html`에 동봉된 것과 **같은** three.js r128을 그대로 떼어낸 것 |
| `glutton_ghoul_viewer_v4.html` | 거대 구울(폭식 구울). 현재의 베이스 |
| `brood_tick_viewer_v1.html` | 포란충(抱卵蟲) — 3막 첫 보스. 팔레트를 **3막**에서 역산했다 |
| `brood_tick_larva_viewer_v1.html` | 새끼 포란충 — 3막 일반 몹. 위 보스의 유생. 팔레트를 **보스 출력색에 맞춰** 역산했다 |
| `corrupted_king_viewer_v14.html` | 부패한 왕 — 90층 보스. 팔레트를 **3막**에서 역산했다 |
| `smoke.js` | **뷰어가 열면 실제로 보이는지** 확인한다. 커밋·전달 전에 반드시 돌릴 것 |
| `build-standalone.js` | three.js를 인라인해 단일 파일을 만든다(사람에게 보낼 때 씀) |
| `export-glb.js` | 캐릭터를 glTF 바이너리(.glb)로 뽑는다 |
| `GLTFExporter.js` | three r128 동봉본의 익스포터(위 스크립트가 주입해 쓴다) |

## 렌더 환경은 게임에서 그대로 옮겨 온 것이다 — 값을 고치지 말 것

뷰어에서 본 것이 게임에서 그대로 나오게 하려고, 게임의 렌더 경로를 통째로 복사해 두었다.
**여기 있는 상수를 '보기 좋게' 바꾸면 뷰어가 거짓말을 하기 시작한다.**

- 저해상도 버퍼 `computeLowRes` (px 모드 세로 **320** 고정, `?pxh=N` 으로 조절 — 게임과 같은 플래그)
- `toneMappingExposure = 1.1`, ACES, px 모드에서 `BasicShadowMap`
- 조명 셰이더 청크 3종: `?dspec`/`?dlight` (깊이), `?drough` (러프니스), `?spec` (전체 밝기).
  **머티리얼을 하나라도 만들기 전에** `THREE.ShaderChunk.lights_fragment_end`를 갈아끼워야 한다 —
  three의 프로그램 캐시 키에 청크 내용이 안 들어가서 나중에 바꾸면 예전 프로그램이 재사용된다.
- 노멀 패스(1패스 노멀 → 2패스 피부 표식) + 블룸 + 포스트 셰이더 전문(외곽선·색보정·채색그림자·
  대기원근·비네트·색 양자화/디더) + 픽셀 스냅
- 막별 환경값(배경·안개·대기색·그림자색·블룸 임계·환경광·달빛·반구광) — `ACTS` 표. 2막만 블룸 0.70
- 조명 리그: 환경광 + 횃불 + 근접광 + 시야광. 게임과 같은 색·세기·사거리

### 조명 모드는 둘이다 — 스튜디오 / 막

`조명` 버튼이 **스튜디오 → 1막 → 2막 → 3막**을 돈다.

- **스튜디오(기본)**: 처음 올라온 뷰어(`glutton_ghoul_viewer v3`)의 조명을 **값 그대로** 가져온 것.
  환경광 `0x6b6070` 0.72 / 키 방향광 `0xfff0e2` 1.15 at (-4, 10, -5) / 림 방향광 `0x6f86c0` 0.6 at
  (5, 3, 5) / 언더 점광 `0xb07a86` 0.45. 그림자 카메라 범위까지 원본 값이다.
  **카메라를 따라 돈다**(턴테이블). 원본은 월드 고정이었지만, 그러면 돌려서 뒤를 볼 때 캐릭터가
  통째로 그늘로 들어가 형태를 못 본다 — 실측으로 각도별 휘도가 42.1~96.0(편차 53.9)까지 흔들렸고,
  따라 돌게 하니 71.3~81.1(편차 9.8)로 고르다. 회전량은 `camYaw - GAME_YAW`라
  **기본 시점에서는 회전이 0** 이고, 그때 빛 배치는 원본과 정확히 같다(양쪽 다 휘도 75.4).
  그림자도 켠 채로 연다.
  안개·대기 원근은 끈다 — 원본은 카메라가 6~7칸 거리라 안개가 모델에 닿지 않았고 대기 원근도
  없었다. 이걸 켜 두면 같은 조명을 넣어도 원본처럼 보이지 않는다.
- **1/2/3막**: 게임 던전 리그 그대로(횃불·근접광·시야광이 플레이어 자리에 붙는다).
  이쪽으로 넘기면 게임처럼 캐릭터 그림자가 꺼지고 발밑 블롭만 남는다.

**두 모드는 색이 다르게 보인다. 색 판단은 반드시 막 모드에서 할 것.**

| | 평균 휘도 | 평균 채도 |
|---|---|---|
| 스튜디오 | 75.5 | 0.478 |
| 1막(게임) | 60.1 | 0.233 |
| 2막(게임) | 65.7 | 0.318 |

스튜디오가 채도 2배로 나오는 것은 조명 탓이 아니라 안개·대기 원근이 없어서다(게임은 그 깊이에서
채도를 상수로 −31.5% 깎는다). 형태를 보는 모드이지 색을 보는 모드가 아니다.

### 게임이 렌더를 고치면 여기도 따라가야 한다

이 뷰어의 값어치는 전부 '게임과 같다'는 데서 나온다. 게임 쪽 렌더가 바뀌면 **반드시 맞춰야 한다.**
안 맞추면 뷰어가 조용히 거짓말을 시작한다.

- **v739~v740 · v753: 픽셀 크기.** `PX_FIXED_H` 가 360 → 288 → **320** 으로 바뀌었다(작을수록 픽셀이 크다).
  안 맞추면 `1.0× = 게임 실제 픽셀 크기` 라는 배지가 거짓이 된다 — 실제로는 25% 더 크다.
- **v732~v738: SSAO.** 포스트 패스에 화면공간 AO 가 들어갔는데, **뷰어에는 옮기지 않았다.**
  캐릭터에 영향이 0 이기 때문이고, 그건 재서 확인했다(아래).

#### SSAO 를 안 옮긴 근거

게임을 띄워 오크 보스를 벽에서 먼 자리에 세우고, **같은 페이지 안에서** `uAOStr` 유니폼만
껐다 켜서 비교했다(페이지를 새로 열면 레이아웃이 달라져 비교가 안 된다).
몬스터 픽셀은 몬스터를 숨겼다 켜서 골라냈다.

| | 픽셀 | 평균 차 | 최대 차 |
|---|---|---|---|
| 몬스터 | 4,411 | **0** | **0** |
| 배경(바닥·벽) | 363,589 | 0.03 | 11 |

표식 구조상 당연한 결과다. 캐릭터는 피부 표식(`isSkinTag`)이라 **받는 쪽에서 제외**되고,
건축물 표식(`markArch`)이 없어 **가리는 쪽에서도 제외**된다. `markArch` 가 붙는 것은 건물과
벽 타일뿐이고 바닥에는 안 붙는다. 즉 벽에서 떨어진 캐릭터에게 SSAO 는 아무것도 하지 않는다.
`?ssaoarch=0` 으로 모든 물체가 가림을 만들게 하면 얘기가 달라지므로, 그 모드를 기본으로 삼게
되면 그때는 옮겨야 한다.

### 광원은 캐릭터가 아니라 '플레이어 자리'에 붙는다

게임에서 던전을 밝히는 광원은 전부 플레이어에게 달려 있고, 몬스터는 몇 칸 떨어져서 그 빛을 받는다.
광원을 캐릭터 안에 두면 안쪽에서 밝혀지는 전혀 다른 그림이 나온다. 그래서 뷰어는 캐릭터에서
`PLAYER_DIST`(3칸) 앞에 플레이어 자리를 만들고 거기에 리그를 얹는다. 카메라를 돌리면 플레이어도
같이 도는데, 이게 '플레이어가 몬스터 주위를 돌면서 보는 것'과 같아서 맞다.

### 확대는 카메라를 당기지 말고 FOV를 좁힐 것

깊이 기반 조명의 램프가 20~33이라, 카메라를 가까이 옮기면 램프 밖으로 나가 밝기가 통째로 달라진다.
FOV만 좁히면 거리·각도가 그대로라 망원 크롭이 되어 조명·원근 왜곡은 게임 그대로다.
`camZoom`이 그 배율이고 배지에 항상 뜬다 — **1.0×가 게임에서 실제로 보이는 픽셀 크기다.**
기본값 3.5×는 보기 편하라고 넣은 것일 뿐이니, 디테일이 실제로 읽히는지는 1.0×에서 볼 것.

### 카메라 거리 26.46은 잰 값이다

게임을 띄워 직접 쟀다. 카메라는 idle일 때 지연 없이 정확히 플레이어 + `(11.07, 20, 11.07)`
= 거리 25.399에 있고, 근접 교전 중인 몬스터의 뷰 깊이는 **26.46**이다(1.06 더 깊다).
25.40으로 두면 깊이 램프 때문에 뷰어가 7% 밝게 나온다.

### 게임과 같은지 확인한 방법

같은 회색 구(`getLowPolyMat(0x808080)`, 반지름 1)를 게임과 뷰어에 똑같은 자리에 놓고 픽셀을 쟀다.

| | R | G | B | 휘도 | 프로브 픽셀 | 뷰 깊이 |
|---|---|---|---|---|---|---|
| 게임(오크 보스 테스트) | 124.1 | 124.2 | 112.4 | 123.3 | 1,042 | 26.46 |
| 뷰어(1막) | 125.8 | 125.9 | 113.3 | 124.9 | 899 | 27.01 |

FOV는 소수점 4자리까지 일치(79.2796). **휘도 차 1.3%, 채널당 최대 1.7/255.**

**프로브 픽셀은 반드시 '분리'해서 골라낼 것.** 화면 좌표에 고정 사각형을 잡아 평균을 내면
프로브가 벽·바위에 조금이라도 가리는 순간 배경을 함께 재게 되어 숫자가 통째로 틀린다
(실제로 그렇게 재서 게임 66 / 뷰어 132 라는 엉뚱한 결과를 얻고 회귀로 오판할 뻔했다).
프로브를 껐다 켜서 **달라지는 픽셀만** 세면 가림과 무관하게 맞는 값이 나온다.

## 베이스에 이미 들어 있는 것 — 새로 짜지 말 것

- **게임과 같은 머티리얼 헬퍼**: `getLowPolyMat`(러프니스 0.9/0.6·메탈니스 0/0.3 — 게임 값 그대로),
  `markOrganic`, `smoothSkinNormals`, `jitterGeometry`. 이름·동작이 같아서 옮길 때 그대로 붙는다.
- **살덩이 헬퍼**: `lump`(울퉁불퉁한 혹), `tumorShell`(타원면을 혹으로 뒤덮기),
  `addSeam`(정맥/균열), `addSpike`(가시), `blade`(표면을 타고 도는 칼날 조각).
- **드로우콜 병합**(`mergeStatic`/`mergeGeos`): 움직이지 않는 조각을 머티리얼별로 하나로 합친다.
  구울은 이걸로 380여 개 → 20개 미만. **애니메이션으로 움직일 그룹은 `skip` 인자로 빼 둘 것.**
- **발밑 블롭 그림자**: 게임 몬스터는 진짜 그림자를 던지지 않는다(`castShadow=false`). 보스는 지름 2.3.
  뷰어의 `sh()`도 같게 맞춰 두었고, 모델링 중 형태를 보려면 `그림자: 스튜디오` 버튼으로 켠다.
- **버튼**: 막 전환(1/2/3막) · 그림자 · 그리드(좌표 숫자 격자) · 게임 시점(각도·배율 리셋).

## 손대기 전에 알아 둘 것

- **정면은 로컬 -z. 게임과 같은 규약이니 절대 뒤집지 말 것.**
  게임은 `rotation.y = Math.atan2(dx, dz) + Math.PI`로 로컬 -z를 표적에 맞추고, 눈·이빨 같은
  얼굴 부품을 전부 음수 z에 둔다(플레이어 -0.32, 일반 몬스터 -0.30, 유령 기사 -0.41 …).
  뷰어도 최상위 그룹을 돌리지 않아서, **게임 몬스터가 `rotation.y = 0`일 때와 똑같은 자세**로 서 있다.
  정면을 보려면 카메라가 -z 쪽에 서야 하므로 `GAME_YAW`가 π다 — **모델이 아니라 카메라를 돌릴 것.**
- **색은 반드시 이 뷰어에서, 그것도 재서 고를 것.** 아래 절도 함께 볼 것.
- 저해상도 버퍼는 **화면과 같은 가로세로 비율**이어야 한다. 가로·세로에 각각 하한을 두면
  세로 화면에서 모델이 찌그러진다.
- r128의 `WebGLRenderTarget.setSize()`는 `depthTexture`를 안 줄인다 — `onResize`에서 손으로
  맞춰야 리사이즈 후 외곽선이 안 깨진다.

### 모바일에서 버튼을 누르면 화면이 위로 밀리는 문제

아랫줄 버튼을 누를 때만 캐릭터 윗부분만 보이게 밀리는 증상이 있었다. 원인이 셋이고 전부 막아 뒀다.

- **`100vh` ≠ `100dvh`.** 예전에는 `body`가 `100dvh`인데 캔버스가 `100vh`였다. 모바일에서 `100vh`는
  '주소창이 숨은 상태'의 큰 높이라 캔버스가 body보다 커지고 문서에 스크롤 여지가 생긴다.
  이제 `html`·`body`·캔버스를 전부 `position:fixed; inset:0`으로 두어 스크롤될 여지 자체를 없앴다.
- **버튼 포커스.** 포커스된 요소가 보이는 영역 밖에 걸쳐 있으면 브라우저가 그걸 보이게 하려고
  문서를 스크롤한다 — `overflow:hidden`으로도 못 막는다. 화면 맨 아래 줄 버튼만 증상이 난 이유다.
  `mousedown`을 막아 포커스를 안 주고, 클릭 뒤 `blur()`도 한다(확인: 탭 후 `activeElement`가
  `gridBtn` → `BODY`로 바뀐다).
- **더블탭 확대.** 버튼을 연달아 누르면 더블탭으로 잡혀 탭한 지점(=아래쪽) 기준으로 확대된다.
  `.btn`에 `touch-action: manipulation`.

크기는 `window.innerHeight`가 아니라 `visualViewport`에서 받는다 — 인앱 뷰어·주소창 때문에
`innerHeight`가 실제로 보이는 높이보다 클 수 있고, 그러면 캔버스 아래쪽이 화면 밖으로 나가서
가운데 맞춰 둔 캐릭터가 위로 치우쳐 보인다.

## 색 고르기 — 감으로 찍지 말고 역산할 것

### 베이스 0x60 위는 화면에서 전부 같은 색이다

프로브 구를 놓고 무채색 베이스를 바꿔 가며 최종 출력을 재면 이렇다(y=1.7, 1막).

| 베이스 | 16 | 32 | 48 | 64 | 80 | 96 | 128 | 192 | 240 |
|---|---|---|---|---|---|---|---|---|---|
| 출력 | 45 | 79 | 94 | 105 | 111 | 116 | 120 | 126 | 132 |

**0x60 위로는 사실상 평평하다.** 근접 교전 거리(3칸)에서 광원이 세서 그 위는 클리핑되기 때문이다.
거기에 포스트 체인이 채도를 상수로 깎는다 — 대기 원근이 `smoothstep(0.5, 0.8, 26.5)`라 깊이와
무관하게 항상 최대여서 채도 −31.5% + 대기색으로 27% 물들고, 안개가 배경색 쪽으로 36% 더 당긴다.

그래서 **원화의 밝은 색을 그대로 넣으면 안 된다.** 구울의 예전 팔레트는 `0x69`~`0xff`로
전 구간이 죽은 영역에 들어가 8단 그라데이션이 통째로 같은 회색(`#74746c`~`#7e7e72`)으로 뭉갰다.
지금 팔레트는 `0x16`~`0x8c`다.

| | 평균 채도 |
|---|---|
| 예전 팔레트(스튜디오 조명에서 고른 것) | 0.108 |
| 역산한 팔레트 | **0.172** |

밝은 쪽만 그런 게 아니라 **어두운 쪽은 반대로 응답이 가파르다**(16→45, 32→79). 빛이 약한
부위는 베이스가 그대로 드러나므로, 한 색으로 밝은 데와 어두운 데를 동시에 맞출 수는 없다.

### 역산 절차

1. rAF를 끊어 장면을 정지시킨다(`window.requestAnimationFrame = () => 0`). 호흡 애니메이션이 픽셀을 흔든다.
2. 프로브 구를 캐릭터 자리에 놓는다. 재질은 실제로 쓸 것과 같게(살이면 `markOrganic`까지) —
   유기체 표식이 있으면 스펙큘러가 없어서 응답이 다르다.
3. **재질이 실제로 놓일 높이에서** 잰다. 광원이 플레이어에게 붙어 있어 높이마다 밝기가 다르다.
4. `renderer.readRenderTargetPixels`로 최종 출력을 읽는다(스크린샷보다 빠르고 정확하다).
   마지막 합성만 임시 렌더 타깃으로 돌리면 된다.
5. 목표 출력색을 정하고 감쇠 곱셈 보정으로 20여 회 돌린다:
   `base[c] *= ((target[c]+1) / (out[c]+1)) ** 0.6`. 오차 3/255 이내로 들어온다.

### 이미 있는 캐릭터와 같은 색으로 맞출 때는 프로브를 놓지 말고 그 캐릭터를 직접 잰다

같은 종의 다른 개체(보스 ↔ 새끼)처럼 **화면 출력이 같아야 하는** 경우다. 이때는 목표색을
손으로 정하지 말고 원본 뷰어에서 재질별 출력색을 그대로 뽑아 목표로 쓴다.

재는 법은 프로브 구가 아니라 **메시 격리**다. 그 재질을 쓰는 메시만 켜고 한 번, 전부 끄고
한 번 렌더해서 두 장이 다른 픽셀의 평균을 낸다(바닥도 끈다). 프로브를 새로 놓으면 그 재질이
실제로 놓인 높이·각도·곡률이 아니라 프로브의 것을 재게 된다.

측정 전에 **`animate()`가 매 프레임 덮어쓰는 값을 고정해야 한다.** 발광 세기가 그렇다 —
`eyeGlowMat.emissiveIntensity`는 깜빡이도록 매 프레임 대입되므로, 고정하지 않으면 두 뷰어를
서로 다른 위상에서 재게 되어 비교가 무의미해진다.

**발광 재질은 색으로 못 맞춘다.** 밝기의 대부분이 `emissive`에서 오므로 `color`를 아무리
낮춰도(0x010101까지 내려도) 목표 아래로 안 내려간다. `emissiveIntensity`를 따로 풀 것 —
휘도로 세기를 먼저 맞추고, 그 세기에서 `color`로 색조를 맞추는 2단계다.
새끼 포란충 실측: 세기만 풀면 오차 13/255(파랑이 모자람), 세기 고정 후 색까지 풀면 2/255.
`animate()` 안의 깜빡임 식에도 같은 배수를 곱해 둬야 한다 — 생성자 값만 고치면 첫 프레임에 덮인다.

**베이스가 원본과 크게 달라지는 것이 정상이다.** 새끼의 위쪽 판은 `0x14111a`인데 보스의 같은
자리는 `0x40283c`다. 보스의 그 판은 y=3.45라 빛이 거의 안 닿고 새끼의 판은 y=1.4라 훨씬 밝게
받기 때문이고, **화면 출력은 양쪽 다 54/255로 같다**. 재질 전부 오차 3/255 이내로 들어왔다.

**지오메트리를 고치면 색을 다시 재야 한다.** `rnd()`가 공용이라 메시를 하나 더 넣거나 빼기만
해도 그 뒤의 지터가 전부 달라지고, 그러면 같은 베이스가 다른 출력을 낸다. **형태를 다 잡은
뒤에 색을 마지막으로 풀 것.** 실측으로 확인한 것: 알을 빼자 금빛 이음선이 48 → 53으로 밀렸고,
그 뒤 점액을 빼자 베이스를 안 건드렸는데도 49로 되돌아왔다. **가는 것일수록 심하다** —
이음선은 굵기 0.006짜리 막대라 잰 픽셀의 상당수가 가장자리이고, 거기에 포스트의 색 양자화·
디더 점 패턴이 섞인다. 오차 3~5 구간은 이 흔들림 폭이므로 그 안에서는 쫓아가지 말 것.

**공격 때만 나오는 재질은 정적 측정으로 못 잰다.** 새끼의 `oozeMat`/`poolMat` 은 분비물
방울에만 쓰여 평소에는 씬에 안 보인다 — 측정이 그냥 건너뛴다(픽셀이 0이라 `null`).

### 목표를 정할 때 상한을 먼저 잴 것

높이별로 낼 수 있는 최대 밝기가 다르다(무채색 `0x8c` 기준, 1막).

| y | 0.1 | 1.0 | 1.5 | 2.4 | 2.8 | 3.3 |
|---|---|---|---|---|---|---|
| 상한 휘도 | 119 | 121 | 122 | 119 | 109 | 91 |

### 위를 향한 면은 어차피 어둡다 — 팔레트로 고치려 하지 말 것

던전 광원은 전부 플레이어에게 달려 있고 전방·아래쪽에 있다. 어깨 윗면처럼 위를 보는 면은
반구광밖에 못 받아서 휘도 24 근처에 머문다. 실측으로 확인한 것:

- 상단 2단 베이스를 ×1.8까지 올려도 휘도는 24 → 27.5뿐인데 채도가 0.32 → 0.21로 무너진다.
- 모델을 0.65배(높이 3.9 → 2.5)로 줄여도 24 → 30이다. 키 문제가 아니다.

즉 **이건 게임 조명의 성질이지 색의 문제가 아니다.** 상단을 읽히게 하려면 발광 악센트를 얹거나
실루엣의 덩어리를 아래로 내리는 쪽으로 풀 것.

### 목표는 게임에서 직접 재 온다 — 뷰어끼리만 맞추면 막이 바뀔 때 통째로 틀어진다

3막 개편(v742~v749)에서 실제로 겪은 것이다. 개편 전 3막에서 역산해 둔 포란충 팔레트를
새 3막에 그대로 놓으니 **살덩이의 자홍이 통째로 사라졌다**(새끼 배 채도 0.511 → 0.130,
R이 최저 채널이 됐다). 새 3막이 그늘을 청록으로 칠하기 때문이다(`uShadowColor` 0x3c1a3a →
0x1b4a4a, 세기 0.25 → 0.40, 환경광 0.2 → 0.34).

**이때 예전 출력색을 목표로 다시 풀면 안 된다 — 도달이 불가능하다.** 베이스를 0x01까지
내려도 초록이 12~16 남는다. 청록은 베이스가 아니라 포스트가 그늘 픽셀에 얹는 것이라
베이스로는 못 뺀다.

그래서 **게임 자신이 3막에서 뭘 내고 있는지**를 목표로 삼아야 한다. 실측(62·65·68·70·74층):

| 게임 재질 | 베이스 | 화면 출력 | 읽히는 색 |
|---|---|---|---|
| `corMatFleshB` | `0x7d2036` (어두운 자홍) | [26,32,38] | **청록** — R이 최저 |
| `corMatFlesh` | `0xa82c42` (밝은 자홍) | [44,34,41] | 자홍 유지 |
| `corMatWall` | `0xd6caa6` (아이보리) | [47,55,51] | 올리브 |
| `corFloorMats` 6종 | `0xb8ae90` 계열 | [22~41, 39~52, 40~50] | 어두운 청록회색 |

**휘도 30 아래는 무엇을 넣어도 청록이 된다.** 게임 자신의 어두운 살덩이도 그렇다.
자홍을 지키려면 베이스가 밝은 쪽(`corMatFlesh` 급)이어야 한다. 포란충의 살은 이 값을
목표로 다시 풀었고, 입 안(`mawMat`)처럼 원래 더 어두운 것은 청록으로 두었다 —
게임의 `corMatFleshB`와 같은 자리이므로 그게 맞다.

**바닥 원판은 게임의 바닥 상수를 쓰면 안 된다.** 3막 석재는 `0xb8ae90` 아이보리인데,
그걸 그대로 넣으면 뷰어 원판이 화면을 가득 채우는 크림색 배경이 되어 캐릭터 색 판단을
망친다(게임 바닥에는 석판 텍스처의 어두운 줄눈·그림자·AO가 얹힌다). 여기서도 **실측 출력색**
([33,47,47])을 목표로 원판 색을 역산한다 — 지금 값은 `0x0b1011`이다.

### 참고할 원본이 없을 때는 '예전 뷰어의 출력'을 의도로 삼는다

부패한 왕을 옮길 때가 그랬다. 같은 종의 다른 개체도 없고 게임에 대응 재질도 없다.
이때는 **사용자가 보고 승인한 화면**, 즉 예전 뷰어의 출력색이 설계 의도다. 그것을 재서
목표로 쓰되 **한 배수로 낮춰 도달 가능한 범위로 옮긴다**(부패한 왕은 0.80배).
그냥 쓰면 전부 클리핑이다 — 실측: `cloth` [253,253,252] · `goldHi` [231,232,225] ·
황금 `0xe8bc46` 은 [179,180,160] 로 **색이 통째로 빠져 회색**이 됐다.
그 장면의 상한은 흰색 재질로 재면 알 수 있다(여기서는 [190,187,186]).

**금속은 베이스로 어둡게 못 만든다.** 넓은 금속판은 횃불 하이라이트를 정면으로 받아
베이스를 `0x010101` 까지 내려도 휘도 115 아래로 안 내려간다. 살은 `markOrganic` 이
스펙큘러를 통째로 지우므로 내려가는데, 금속은 그 바닥이 남는다.
그래서 금속은 목표를 정해 역산하는 대신 **베이스를 램프로 훑어 채도가 최대인 지점**을 고른다:

| 베이스 | 0x100802 | 0x301605 | 0x70350b | **0xa04f10** | 0xe8bc46 |
|---|---|---|---|---|---|
| 출력 채도 | 0.05 | 0.11 | 0.17 | **0.20** | 0.08 |

더 밝히면 무너지고 더 어둡게 해도 안 내려간다. **메탈니스는 0.28↔0.0 이 거의 차이가 없고
(실측), 러프니스를 올려 하이라이트를 죽이는 것도 안 통한다**(녹청 휘도 113 → 132 로 오히려
나빠졌다). 게임 기본 금속값을 그대로 둘 것.

**발광 재질은 세기부터 낮춰야 색이 산다.** 예전 뷰어 값 그대로면 전부 흰색으로 날아간다
(`crackMat` [243,243,230]). 휘도로 `emissiveIntensity` 를 먼저 맞추고, 그 세기에서 `color`
로 색조를 맞춘다. **`animate()` 안의 맥동 식에도 같은 배수를 곱할 것** — 생성자 값만 고치면
첫 프레임에 덮인다.

### 게임에서 재는 법

1. `?dev=1`로 열고 `#maxLevelBtn` → `.char-card[data-char="knight"]`를 눌러 시작한다
   (만렙 테스트라야 `godMode`가 켜진다). 그다음 `godMode = true; jumpToFloor(65)`.
2. rAF를 끊고, **메시를 숨기는 대신 그 재질의 색만 형광색(`0xff00ff`)으로 바꿔 두 장을 비교**한다.
   씬이 거대해서 traverse+visible 토글은 느리고, 숨기면 뒤엣것이 드러나 값이 오염된다.
   달라진 픽셀 자리에서 **원래 장(場)의 색**을 평균하면 그게 그 재질의 출력색이다.
3. 층마다 조금씩 다르므로 **여러 층에서 재서 평균**할 것(위 표는 5개 층).

## 드로우콜을 줄일 때 — 색을 버리지 말고 정점색으로 구울 것

드로우콜은 **(병합 그룹 × 재질)** 이다. 즉 **재질 수가 그대로 콜 수**가 된다.
부패한 왕은 살 재질만 8종이라 그것만으로 콜의 절반을 먹고 있었다(132개 중 68개).

색을 줄이는 대신 **정점색으로 구워 넣어 하나로 합친다** — 게임이 3막 산호(`mergeCoral`)에서
쓰는 것과 같은 방식이다. `mergeGeos(geos, cols)` 가 지오메트리마다 그 색을 `color` 어트리뷰트로
쓰고, 공용 재질에 `vertexColors: true` 를 준다. 재질에 `userData.mergeInto` 를 달아 두면
`mergeStatic` 이 알아서 묶는다.

**색 말고 나머지가 같아야 묶을 수 있다.** 그래서 세 무리로 나눈다.

| 무리 | 조건 | 묶은 것 |
|---|---|---|
| 살 | `markOrganic` (하이라이트 없음·러프니스 1.0·피부 표식) | 12종 |
| 금속 | `getLowPolyMat(_, true)` (러프니스 0.6·메탈니스 0.3) | 4종 |
| 단단 | `getLowPolyMat(_)` (러프니스 0.9·메탈니스 0) | 7종 |

발광 재질은 `emissive` 색·세기가 제각각이라 못 묶는다.

실측(부패한 왕): **메시 132 → 45 · 재질 27 → 7 · 삼각형 20,620 그대로.**

### 매 프레임 움직이는 것도 합칠 수 있다 — 단 CPU 로 갱신할 것

발광 핵 11개는 제각각 맥동해서 병합에서 빠져 있었다(콜 11개). 합치는 방법은 셋인데
**이 파이프라인에서 쓸 수 있는 것은 하나뿐이다.**

| 방법 | 결과 |
|---|---|
| 그룹째 스케일 | ✗ 원점에서 떨어진 핵이 제자리에서 부푸는 대신 원점 쪽으로 미끄러진다 |
| 정점 셰이더 | ✗ 색 패스만 흔들리고 노멀·그림자 패스는 제자리라 외곽선이 형상과 어긋난다 |
| **CPU 정점 갱신** | ✓ 지오메트리 자체가 바뀌므로 모든 패스가 같이 움직인다 |

정점마다 '속한 핵의 중심'과 '위상'을 들고 있다가 매 프레임 `center + (base - center) * s` 로
다시 쓴다. 정점이 660개뿐이라 비용은 무시할 수 있다. **콜 11 → 1, 픽셀 차이 0.**
핵마다 다른 위상도 그대로다(실측 t=0 에서 1.000/1.014/1.066, t=1 에서 1.068/0.923/1.003).

**그림이 그대로인지는 픽셀로 확인할 것.** 재질 통합은 0.18%(1,146/630,000)만 달랐고, 그 자리는
칼날·방패 테두리·어깨 결정 — **원래부터 면이 겹쳐 깊이 다툼을 하던 곳**이다. 병합으로 그리는
순서가 바뀌어 승자가 뒤집힌 것이지 색·음영이 바뀐 게 아니다. 양자화를 꺼도 같은 자리에 남는다.

### A/B 를 믿기 전에 대조군이 0 인지 볼 것 — 이 뷰어들은 rAF 만 멈춰서는 부족하다

CLAUDE.md 에 'rAF 를 끊고 대조군 한 쌍을 먼저 찍으라'고 적혀 있는데, **여기서는 그걸로도
모자란다.** rAF 를 멈추기 전 2초 남짓 동안 호흡·흔들림·팔다리 lerp 가 진행되고 그 위상이
로드마다 다르기 때문이다. 실제로 **같은 파일끼리 비교했는데 3.87% 가 달랐다** — 그 상태로
통합 전후를 재고 '4.5% 바뀌었다'고 판단할 뻔했다.

포즈를 손으로 고정해야 한다(`torsoGrp.scale`·`bodyGrp.position/rotation`·`headGrp.rotation`·
`clothGrp.rotation`·팔다리 회전을 REST 로·`glowNodes` 스케일·발광 세기·`bloomLight.intensity`).
그러면 대조군이 **0/630,000** 으로 떨어진다. 거기서부터만 측정을 믿을 것.

### 3막 어둡게 하기(v753)는 반영 완료 — 팔레트는 안 건드렸다

게임이 v753 에서 3막을 한 단 어둡게 했다(`A3DIM`. `COR_LIT` 기본 0.62 라 켜져 있다).
뷰어의 `ACTS[3]` 을 그 값으로 맞췄다 — 배경·안개 `0x090f10`/0.024 · 환경광 0.26 ·
달빛 0.16 · 반구광 0.14. 대기색·그림자색·세기(0x14303a / 0x1b4a4a / 0.40)는 안 바뀌었다.

**팔레트는 다시 풀지 않았다. 그게 맞다.** 어둡게 한 것은 3막 전체에 건 의도적인 변경이고,
게임 안의 몬스터도 같은 팔레트로 같이 어두워진다(게임이 이 뷰어들의 베이스 값을 그대로
쓰고 있는 것을 확인했다 — 포란충 `0x2c2732`/`0x40283c`, 새끼 `0x1f2129`, 부패한 왕
`0x11070f`/`0xa04f10` 이 전부 index.html 안에 있다). 여기서 베이스만 올리면 **뷰어의 몬스터만
방보다 밝아진다.**

캐릭터가 얼마나 어두워졌는지(캐릭터 픽셀 평균):

| | v752 환경 | v753 환경 |
|---|---|---|
| 부패한 왕 | 휘도 109.1 · 채도 0.262 | **79.8 · 0.261** |
| 포란충 | — | 55.6 · 0.314 |
| 새끼 포란충 | — | 50.5 · 0.301 |

클리핑은 0.7% → **0%** 가 됐다. 채도는 유지된다 — 어두워지면서 색이 빠지지는 않았다.

### 게임 쪽 값을 확인할 때는 소스를 대조할 것 — 전역 이름을 믿지 말 것

환경이 맞았는지 회색 프로브로 재려다 틀렸다. 게임의 전역 `torch` 가 플레이어의 횃불일
거라 보고 그 옆에 프로브를 놨는데, 실제로는 플레이어(-30,0,-5)에서 **20 떨어진**
(-25,2.5,-25) 에 있었다(벽 횃불 쪽이다). 그 상태로 잰 값은 게임 [23,41,45] / 뷰어
[104,76,79] 로 4배 차이가 나서 하마터면 '환경이 안 맞았다'고 오판할 뻔했다.

렌더 경로가 맞는지는 **소스를 직접 대조하는 쪽이 정확하고 빠르다.** 포스트 셰이더의
유니폼 값을 이름별로 비교하면(`uSat`·`uCon`·`uSplit`·`uVig`·`uQuant`·`uDither`·
`uQuantGamma`·`uBloomStr`·`uAerialStr`·외곽선) 다른 것이 무엇인지 바로 나온다.
실측 결과 다른 것은 `uAerialColor`·`uShadowColor` 둘뿐이었고, 그 둘은 `applyAct` 가
막마다 덮어쓰는 **초기값**이라 실제 차이가 아니다. 조명 셰이더 청크 3종과 블룸도
주석 말고는 동일했다.

## 예전 뷰어를 게임 렌더 환경으로 옮길 때

부패한 왕(v13 → v14)에서 실제로 걸린 것들. 방법은 **게임 환경이 이미 들어 있는 뷰어를
복사해 몸통 부분만 갈아 끼우는 것**이다(여기서는 `brood_tick_viewer_v1.html`).

**루트의 반바퀴 회전을 빼야 한다.** 예전 뷰어들은 `root.rotation.y = Math.PI` 로 모델을
돌려 놓고 카메라를 거기에 맞췄다. 게임 규약은 '정면 = 로컬 -z' 이고 반바퀴는 카메라
(`GAME_YAW`)가 진다. 확인은 눈이 아니라 숫자로 — 로컬 -z 를 월드로 옮겨 카메라 방향과
내적하면 1 이 나와야 한다(세 뷰어 모두 1.000).

**`sh()` 의 뜻이 반대다.** 예전 뷰어의 `sh()` 는 `castShadow = true` 인데 베이스의 것은
`false` 다(게임 몬스터는 진짜 그림자 대신 발밑 블롭을 쓴다). 베이스 것을 그대로 쓰고
`makeBlobShadow()` 를 붙이면 된다.

**살 재질에 `markOrganic` 을 직접 걸어야 한다.** 전용 빌더가 자기 재질을 만들면 게임의
자동 적용에서 빠진다. 이때 **살이 아닌데 살 재질을 공유하던 곳을 갈라 둘 것** — 부패한
왕은 `fCream` 하나를 살·부츠·방패면에 같이 쓰고 있어서, 그대로 걸면 방패에서 하이라이트가
빠지고 노멀이 뭉갠다.

**공용 헬퍼와 이름이 겹치는 것을 정리한다.** `lump`·`tumorShell`·`addSeam`·`mergeStatic` 은
베이스에 이미 있다. 시그니처가 조금 다르면(부패한 왕의 `tumorShell` 은 `pool` 을 받는다)
**베이스 쪽을 확장**하고 중복 정의는 지울 것 — 같은 이름을 두 번 선언하면 동작은 하지만
어느 쪽이 쓰이는지 읽어서는 알 수 없다.

**카메라 기본값은 모델 높이에 맞춘다**(`target.y` = 높이의 절반, `camZoom` 은 보스 기준
높이 4.0에 3.5). 그리드 축·라벨 범위도 같이 늘릴 것.

**동작 스크린샷은 rAF 를 멈추고 찍어야 한다.** rAF 가 도는 채로 `page.screenshot()` 을 찍으면
`preserveDrawingBuffer:false` 라 **빈 버퍼가 잡혀 새까만 그림이 나온다.** 원인을 모델·조명에서
찾다가 시간을 버리기 쉽다 — 찍기 직전에 `requestAnimationFrame` 을 막고 `renderWithPost(scene)`
를 한 번 직접 부를 것.

**단, 그 방식만으로 검증했다고 여기면 안 된다 — `node viewers/smoke.js` 를 따로 돌릴 것.**
직접 렌더는 **뷰어 자신의 애니메이션 루프가 도는지를 건너뛴다.** 부패한 왕을 옮길 때
`<script>` 태그를 한 줄짜리 주석과 함께 바꾸는 바람에 뒤쪽 줄 번호가 1 밀렸고, 그 상태로
애니메이션 블록을 잘라 내면서 **마지막 줄 `animate();` 이 통째로 사라졌다.** 함수는 정의돼
있고 문법 검사도 통과하고 예외도 안 나므로 — 직접 렌더로 찍은 스크린샷까지 멀쩡했다 —
사용자가 열어 보고 새까만 화면을 보고서야 드러났다. `smoke.js` 는 아무것도 건드리지 않고
띄워 두고 ① rAF 가 실제로 불리는지 ② 드로우콜이 0 이 아닌지 ③ 캐릭터 픽셀이 있는지
④ 오류가 없는지를 본다. 일부러 `animate();` 를 지운 사본으로 잡히는 것까지 확인해 뒀다.

**줄 번호로 코드를 잘라 붙일 때는 앞에서 줄을 넣거나 뺀 적이 없는지 먼저 볼 것.** 같은
실수를 두 번 했다(포란충은 꼬리를 한 줄 늦게 시작해 `renderWithPost(scene);` 를 빠뜨렸다).
번호 대신 **내용으로 경계를 찾고**(`lines.index('...')`), 잘라 낸 블록을 원본과 diff 해서
의도한 차이만 남았는지 확인하는 쪽이 안전하다.

## 일반 몹은 보스와 다른 규칙으로 만든다

새끼 포란충을 만들면서 실측으로 갈린 것들.

**카메라 기본값이 보스용이다.** `target.y`(보스 1.7)와 `camZoom`(3.5)은 4미터짜리 보스에 맞춘
값이라, 1.5미터짜리 몹을 그대로 띄우면 화면 아래 구석에 조그맣게 붙는다. 모델 높이의 절반을
`target.y`로, 배율은 `보스 배율 × 보스 높이 / 새 높이`쯤으로 잡는다(여기서는 0.78 / 8.0).
`ZOOM_MAX`도 같이 올릴 것 — 확대는 FOV로 하므로 조명은 안 변한다.

**게임 실제 크기에서 이 몹은 화면 30픽셀이다.** 그 크기에서 살아남는 것은 실루엣과 색 덩어리
두어 개뿐이다. 이음선·홑눈 하나하나는 안 보인다. 반대로 **보스의 굵기를 그대로 축소하면
다리가 1픽셀 밑으로 내려가 사라진다** — 새끼 다리는 비례로 계산한 값보다 40% 굵게 넣었다.
확인은 `camZoom = 1.0`으로 한 장 찍어 보는 것이 제일 빠르다(배지에 '게임 실제 크기'라고 뜬다).

**드로우콜은 개체 수만큼 곱해진다.** 보스는 한 마리라 마음껏 써도 되지만 일반 몹은 여럿이
동시에 나온다. 실측(캐릭터 본체만): 보스 47메시·7,328삼각형 → 새끼 **23메시·2,600삼각형**
(49% / 35%). 가장 크게 아낀 것 둘:
· 다리 밑동 관절은 다리와 함께 움직이지 않는다. 몸통에 직접 붙이면 다리마다 콜이 하나씩 준다.
· 발톱을 다리와 **같은 재질**로 두면 무릎 그룹이 한 덩어리로 병합된다(어두운 발톱은 이 크기에서
  어차피 안 보인다).

**넘어지는 죽음 연출은 회전축을 옮겨야 한다.** `bodyGrp`의 원점은 바닥(y=0)이라 그냥 `rotation.z`를
주면 몸이 제 발 밖으로 미끄러진다(실측: 73°에서 0.86 만큼 옆으로 날아갔다). 다리 밑동 높이를
축으로 삼도록 `position.x = PIV·sin θ`, `position.y += PIV·(1−cos θ)`를 같이 넣어야
'그 자리에서 옆으로 넘어가는' 그림이 된다.

**`mergeStatic` 이 먹은 메시는 애니메이션이 안 먹는다.** 병합은 자식 메시를 지오메트리로
합치고 씬에서 **제거**하므로, 그 변수에 `scale`을 줘도 아무 일도 안 일어난다(에러도 안 난다).
움직여야 하는 것은 병합에서 빼거나(`mergeStatic(root, [제외])`), 부모 그룹을 대신 움직일 것.

**발끝을 y=0에 딱 맞춰 풀었으면 떨림은 한쪽 방향으로만 줘야 한다.** 벌레다운 잔떨림을
`sin()`으로 양쪽으로 주면 그 진폭만큼 발이 바닥을 뚫는다(실측 −7mm). `-|sin()|`으로 바꿔
드는 쪽으로만 흔들면 발끝 최저가 +0.2mm다.

## 확인하는 법

```bash
# 1) 문법
S=$(grep -n '^<script>$' viewers/<파일>.html | tail -1 | cut -d: -f1)
E=$(grep -n '^</script>$' viewers/<파일>.html | tail -1 | cut -d: -f1)
sed -n "$((S+1)),$((E-1))p" viewers/<파일>.html > /tmp/v.js && node --check /tmp/v.js

# 2) 실제 렌더 — 정적 서버로 띄우고 동봉 Chromium 으로 스크린샷
npx http-server -p 8125 -s &

# 3) 사람에게 보낼 단일 파일(three.js 인라인)
node viewers/build-standalone.js viewers/<파일>.html
```

Playwright는 `executablePath: '/opt/pw-browsers/chromium'`로 동봉본을 직접 가리킬 것
(`playwright install`을 받지 말 것). 실행 인자는
`['--enable-unsafe-swiftshader','--use-gl=swiftshader','--no-sandbox']`.

게임 자체를 띄워 비교하려면 `?dev=1` → 언어 선택 → `#bossTestBtn` → 보스 이름 → `#bossTestExit`.
UI를 숨기겠다고 `body > *:not(canvas)`를 감추면 안 된다 — 캔버스가 `#app` 안에 들어 있어서
같이 사라지고 화면이 까맣게 나온다.

## 3D 모델 파일로 뽑기 (.glb)

```bash
node viewers/export-glb.js viewers/<이름>.html            # 기본 자세
node viewers/export-glb.js viewers/<이름>.html --pose=phase2
node viewers/export-glb.js viewers/<이름>.html --pose=roar
```

`viewers/dist/` 에 `.glb` 가 떨어진다(저장소에는 커밋하지 않는다). Blender·윈도우 3D 뷰어 등에서 바로 열린다.

이 캐릭터는 코드로 생성되므로 파일에 저장된 메시가 없다. 그래서 스크립트가 헤드리스 브라우저로
뷰어를 띄우고, **실제로 만들어진 씬 그래프를 그대로** 내보낸다.

**나오는 것**: 지오메트리 · 머티리얼(색·러프니스·메탈니스·발광) · 계층 구조.
**안 나오는 것**은 두 가지고 둘 다 원리상 그렇다.

- **애니메이션.** 이 뷰어의 동작은 키프레임이 아니라 매 프레임 도는 자바스크립트다.
  특정 순간이 필요하면 `--pose` 로 그 자세를 만들어 정지 포즈로 내보낸다.
  (포즈는 `animate()` 를 여러 번 부르지 않고 최종값을 직접 넣는다 — 이 뷰어의 동작은 dt 기반
  lerp 라서 루프를 빨리 돌리면 dt 가 거의 0 이라 수렴하지 않는다.)
- **게임의 후처리.** 픽셀화·외곽선·색보정·안개는 렌더 파이프라인이지 모델이 아니다.
  그래서 Blender 에서 열면 뷰어보다 밝고 매끈해 보이는 게 정상이다.

**`flatShading` 은 손으로 구워 넣는다.** three 렌더러 쪽 설정이라 glTF 에 대응하는 항목이 없어서,
그냥 두면 각진 로우폴리 느낌이 통째로 사라진다. 그 머티리얼을 쓰는 지오메트리는 비인덱스로 바꾼 뒤
`computeVertexNormals()` 를 불러 면 노멀을 넣는다(구울 기준 16개 메시). `markOrganic` 이 걸린 살
재질은 `flatShading` 이 이미 꺼져 있어 부드러운 노멀 그대로 나간다.
발밑 블롭 그림자는 모델이 아니라 렌더 트릭이라 빼고 내보낸다.

구울 실측: 66 메시 / 삼각형 18,732 / 머티리얼 23 / 4.35 × 3.82 × 2.59 / 1.4MB.
다시 읽어들여 확인했고 숫자가 그대로 나온다(포즈 파일은 열린 배 때문에 깊이가 2.59 → 2.78,
포효는 팔을 벌려 폭이 4.35 → 4.89 로 바뀌는 것까지 반영된다).

## 게임으로 옮길 때

게임 쪽 캐릭터는 `createAdvancedMonster`(index.html)에서 타입별로 분기하고, 덩치가 큰 것은
전용 빌더(`buildXxxBody`)를 따로 둔다. 옮길 때 잊기 쉬운 것:

- 방향축은 이미 맞다(위 참고). 최상위 그룹 아래를 통째로 게임 쪽 `grp`에 붙이면 그대로 앞을 본다.
- **살·피부 재질에 `markOrganic`을 직접 걸 것.** 전용 빌더가 바깥 `skinMat`을 가리고 자기 재질을
  만들면 자동으로 안 걸린다(궁중 마법사·혼령이 실제로 이렇게 빠져 있었다). 돌·금속 몸이면 반대로
  제외 목록에 넣는다. 뷰어에서 이미 걸어 두었으니 그 목록을 그대로 가져가면 된다.
- 조명·후처리는 옮길 필요가 없다 — 게임에 이미 같은 것이 있다. 뷰어에서 가져갈 것은 몸통 코드뿐이다.
